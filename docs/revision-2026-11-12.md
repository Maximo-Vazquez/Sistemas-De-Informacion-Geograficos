## Acceso con Google

El README pide `GOOGLE_CLIENT_ID` y `GOOGLE_CLIENT_SECRET`, y registra el callback local. `config/settings/base.py` confirma allauth con Google como único proveedor. Las vistas del panel y del visor usan `login_required`.

El cliente OAuth debe ser de tipo **Aplicación web**, porque Django recibe la redirección. Se configura una aplicación en Google Cloud con una cuenta existente; no se crea otra cuenta personal. Si el equipo ya tiene un cliente, se puede reutilizar con el callback local autorizado.

Se creó un `.env` local ignorado por Git, con la configuración de desarrollo y una clave Django aleatoria. En una continuación de la sesión, el usuario proporcionó el JSON del cliente web desde una carpeta externa al repositorio. Se validaron los callbacks de `localhost` y `127.0.0.1`, y se cargaron ID y secreto sin mostrarlos en las salidas.

Se aplicó el `.env` al contenedor `visor-sig-web`, con permiso de lectura y escritura solo para su usuario de aplicación, y se reinició Django. `manage.py check` pasó. Una solicitud HTTP real de inicio OAuth por POST con CSRF válido respondió 302 hacia `accounts.google.com`, con el cliente configurado y el callback exacto de localhost. El ingreso completo a Google debe realizarlo el usuario en el navegador; todavía no se verificó el intercambio final del código ni la sesión autenticada.

Las credenciales permanecen en el `.env` local y en el contenedor actual. Al recrear ese contenedor, se deben pasar nuevamente mediante `--env-file .env` o el mecanismo de secretos correspondiente. El JSON original no se copió al repositorio.

Actualización posterior: se incorporó el servicio `web` de Compose con `env_file: .env` y `runserver` para desarrollo. Sustituye al contenedor manual que usaba Gunicorn sin nginx y devolvía 404 para JavaScript y CSS. Las páginas de inicio y login ahora entregan sus siete assets referenciados con HTTP 200 y el inicio OAuth conserva la redirección correcta. El usuario confirmó mediante capturas el acceso autenticado al visor y la visualización del mapa base. El contenedor manual anterior se conserva detenido.

La guía paso a paso está en el README. Referencias oficiales: [clientes OAuth](https://support.google.com/cloud/answer/15549257?hl=es) y [flujo de servidor web](https://developers.google.com/identity/protocols/oauth2/web-server).

## Verificación local

- PostgreSQL y GeoServer: contenedores saludables; extensiones y tablas consultadas por SQL; catálogo de GeoServer consultado por REST.
- Se creó el espacio `ign`, ausente en esta instalación. WMS y WFS respondieron HTTP 200 con documentos de capacidades válidos. No hay capas publicadas.
- Frontend: dependencias del lockfile instaladas; `pnpm build` pasó TypeScript y Vite; `pnpm check:colores` pasó. Assets disponibles en `static/frontend/`.
- Django: el contenedor existente pasó `manage.py check`, los 13 tests con `config.settings.test` y `ruff check .`.
- Inicio y login: HTTP 200. El visor sin sesión redirige al login; el HTTP 200 posterior corresponde al formulario de acceso, no a un visor autenticado.
- Tras aplicar las credenciales reales, inicio OAuth por POST con CSRF: HTTP 302 a Google con el ID y callback esperados. No se imprimieron secretos ni el estado de la sesión OAuth.
- No se realizó una revisión visual del visor en navegador ni una prueba real de Google. Las comprobaciones del contenedor corresponden a su imagen existente, sin montaje del código local.
- La instalación Python nativa no se completó: `psycopg-binary==3.3.6` no ofrece una distribución compatible con el Python Windows ARM instalado. El entorno virtual no está listo para iniciar Django; la aplicación comprobada corre en Docker.
